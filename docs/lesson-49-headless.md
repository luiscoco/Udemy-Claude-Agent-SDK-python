# Lesson 49: headless processes and CI

The owned fixture contains clean and buggy Python sources, a child machine-result program and a one-slot local HTTP worker. The host launches exact executable and argument vectors without a shell, with a separate configuration home and small environment. Standard input reaches EOF, while stdout and stderr are read separately with a 64 KB cap. On a deadline, overflow or task cancellation, the host kills and awaits its owned child.

`mapped_exit` is an explicit teaching policy: 0 for a successful child and complete accepted result; 10 for a nonzero child close; 11 for missing or unsuccessful terminal evidence; 12 for permission denials; 124 for timeout; 127 for missing executable; 130 for cancellation. These are not claimed to be Claude CLI's native exit codes. A valid FAIL report on the buggy source yields CI code 20. The checker requires exact run, verdict and issues fields, plus unmodified fixture hashes.

The native Headless action runs the installed Claude CLI with a fixed JSON schema and the Python Agent SDK in separate owned homes. Both use Haiku, no external tools, fixed sources, process deadlines and independently checked UUID, result and cost fields. The native CI action classifies clean and buggy files separately. The API exposes fixed actions through `/api/c49`, enforces local versus live options and fresh consent, and saves only passing state. The browser shows process and worker receipts, source excerpts, three source-aligned narration clips, seven explained questions and two distinct SVG diagrams.

The Deploy action demonstrates local worker lifecycle: health and readiness return 200, one admitted job occupies the slot, a second receives 429, drain changes readiness to 503, release completes the admitted job, and a fresh TCP connection fails after exit. A separate test withholds release and observes a real 408 job deadline before clean closure. The Node.js reference IPC is adapted to Python child stdout JSONL and nonce-protected loopback control endpoints. The Dockerfile, ignore rules and CI YAML are examples only; no image or cloud deployment is claimed.
